# Flows

## Purpose

The repo's pipelines: a DAG of steps saved as `.cinder/flows/<name>.yml`, and their runs.

## Where

Automation ▸ Flows, for the current repo (`/:repo/flows`); the top bar reads Automation › Flows › *repo* › *branch*

## What you can do

- On a repository with no code: an empty state with **Quick setup** (opens Code) instead of the page's data.
- Tabs **Runs** and **Designer**. The bar shows the repo and the target branch: the one picked in the top bar (`?target=<branch>`), else the default branch.
- Runs: tiles for Runs, Pass rate, Median duration (first step start to last step finish, over runs whose steps all finished) and Waiting for approval (runs with an open Flow approval item); with no runs in range the last two read —. Each run card shows the run's id (any change id in it as its first 8 characters, the full id on hover and copy) and commit and a pip per stage coloured by its status, and opens the run page. **Run flow** (runs the flow from the target branch's head), search runs, runs per hour over a time range, and run detail with each step's state. Under run detail, a **Quarantined** card ("ran, but excluded from the verdict") lists the repo's quarantined tests: this run's result at the run's commit (failed · ignored, passed, skipped, or not run, as flow runs don't record test results), flake rate (flakes/runs) and since when, with **Manage** opening Repo settings ▸ Flaky checks. It is absent when no test is quarantined.
- Run page (`/:repo/flows/runs/:id`): one screen, with the header and stage graph on top and each pane scrolling on its own. The header has **All runs** (back), the run's status, flow name and run number, a status pill, and, for a run started by a push to a change, that change with its title. **Cancel run** shows while the run is queued or running; a finished run has **Re-run all**, and a failed one also **Re-run failed jobs** (failed, skipped and cancelled jobs). A re-run shows its jobs queued at once and goes back with the error if the server refuses it. **Hide graph** / **Show graph** toggles the stage graph. A meta row shows the branch, commit, actor, start time, wall time, the worker pools that ran its jobs and the repo; it hides when the window is under 860px tall. The stage graph shows a column per stage (its status and passed/total) with a chip per job and leg (status, name, duration), joined by connectors; clicking a chip selects that job (`?job=`). Below the graph, a job tree (a 220px list above the content below 900px wide) lists **Summary**, then each stage (click to collapse or expand) with its jobs' status and duration; the selected job lists its steps. Without `?job=` the first failed job is selected, else the first running job, else Summary; `[` and `]` select the previous and next job. With Summary selected, the content area shows tiles for Status, Wall time, Sandbox time and Judge tokens, the run's annotations (click one to select its job), a jobs table (click a row to select the job), a steps table (each job's steps, including the runner's own, with job and duration), a tests table per suite and job, and the artifacts with a **Download** link each (kept 30 days). Job and stage statuses and new annotations update in place while the page is open. With a job selected, it shows the job's log:
  - A header with the stage and job, status and duration, instance type, worker (managed or BYO) and attempt, and **Re-run job** once the job has finished.
  - A toolbar: search (`/` focuses it; Enter and Shift+Enter or ▲ ▼ step through the matches, with an n/m counter), the **Timestamps** clock toggle (an `HH:MM:SS` gutter, UTC), the **Wrap long lines** toggle (line numbers stay beside their wrapped line), **Follow** (running jobs only: keeps the newest line in view; scrolling up turns it off), **Expand all** / **Collapse all**, and **Raw** (downloads the job's `log.txt`). A search loads every step's lines. Terminal colour and bold codes in a line show as colour and bold; other escape codes are removed.
  - An annotations strip, one row per error or warning; a click opens its step and groups, scrolls to the line and highlights it.
  - Each step as a fold with a sticky header (caret, status, name, duration). Failed and running steps and steps with a search hit open by default; a step's lines load when it opens. Lines are numbered per step and each number links `?job=<key>&L=<key>-<step>-<line>`; opening such a link opens the step and its groups, scrolls to the line and highlights it. `[command]` lines show a `$` prompt in strong weight, `##[error]` and `##[warning]` lines a tinted row reading "Error:" or "Warning:", and lines are coloured for success, failure, warnings, source and quiet output.
  - Before a job's steps, **Set up job** lists the worker's runner name, its operating system and CPU count, the repository token's access (read-only, for the checkout), the egress mode and allowed hosts, the Keystore secrets injected into the job (names only), an **Environment** group with the job's env (any value that is a secret or env value shows as `***`; secrets show as `NAME=***`), the workflow directory and commit, and the job name. **Checkout** then shows the repository, commit, depth and how long the fetch took. After the job's steps, **Upload artifacts** (only when a step has `junit:` or `artifacts:`) sends the test reports and artifacts of every step that ran, even after a failed step, and **Complete job** removes the workspace and says how long the steps took. Each folds, shows its status and duration, and numbers and links its lines like any step. A flow of plain steps (no `job:`, matrix, shards or retries) shows **Set up job** and **Checkout** on its first step's job and **Complete job** on its last. An environment sync's run shows **Set up job** (the plan, secrets, resources, migrations and the uploaded version), one step per traffic percentage (the split deployed and the health check), and **Complete job** (synced, rolled back or failed).
  - `##[group]` … `##[endgroup]` fold inline, indented 18px per level; a group holding an error, a failed test or a search hit opens by itself.
  - A running step ends in a "waiting for output…" row; new lines append as the worker sends them, without redrawing the lines already shown or moving the scroll position. A log over 2,000 lines draws only the lines near the visible window. An unknown run id shows **Run not found** with a link back to the runs.
- Designer: lists the target branch's `.cinder/flows/*.yml` grouped by trigger: **On a change**, **On push**, **Scheduled**, and **Manual** for flows that only run by hand (a flow with several triggers sits under the first of those). Each card shows the last run's status, the flow's name and triggers, its runs count and a pass/fail bar over its last 30 finished runs; below the repo's trust threshold (200 outcomes unless set in Repo settings) it reads "untrusted: n outcomes". A run's update refreshes the cards live. The cards draw from the flow list alone; the canvas loads the opened flow's file, and shows **Couldn't load this flow.** with **Retry** when that fails. **Save as change** opens a change against that branch. Pick a flow or **New flow**; **Graph**, **Split** (graph and YAML side by side, with line numbers and the selected step's line highlighted) or **YAML** view; the YAML shown is the exact text **Save as change** writes. The toolbar has **Undo** / **Redo** (`Ctrl Z` / `Ctrl Shift Z`, the last 50 edits of the flow: steps, dependencies and positions), zoom **−**, the zoom % (click for 100%), **+** and **Fit**, and `Ctrl`+wheel zooms 50%–150% around the pointer. The canvas is a dotted grid with lanes Trigger, Stage 1 … n; drag its empty part to pan, and click the minimap (bottom right, with the visible area outlined) to jump there. The trigger node feeds the first-stage steps with dashed edges; clicking it opens the inspector's Flow tab. Each step shows its type, name, subtitle, its status and duration in the last run (or "not run yet"), and `×n` for a matrix of n legs; the edge into a step that is running is animated (static with reduced motion). Hover a step and click **+** to add a Command step after it. **Add a step** (command, verify, Cloudflare Workflow, deploy, approval) is a column beside the canvas, a row below 1000px: click a type to add it, or drag it onto the canvas to place it at the pointer. Drag to connect steps, set a Command step's **Matrix** (`node: [18, 20]`, saved as `matrix: { node: [18, 20] }`; text that doesn't read as `axis: [values]` shows the matrix error and blocks Save as change), set Runs after, **Remove dependency**, **Delete step**, **Auto layout**, **Validate**, **Dry run**, **Save as change**. The inspector's **Step** tab edits the selected step: name, type and its fields, Runs after, Condition, and (except an approval gate) **Worker pool** (Workers' managed and BYO pools, saved as the pool's labels in `runs-on`), **Timeout**, **Retries** and **Secrets** (checkboxes of the Keystore names for this repo and global ones, "Injected from Keystore at run time"; empty for someone without `keystore.read`). With nothing selected it shows a hint and a count of steps per type and of dependencies. The **Flow** tab sets the triggers (a change, push, a schedule with a UTC cron, manual), **Concurrency** (`concurrency: cancel | queue | parallel`) and the **Default worker pool** (the flow's `runs-on`, used by jobs that set none), and notes that flows are read from the target branch. **Validate** shows the flow's validation messages word for word, or "Valid. n steps, m dependencies, no cycles." **Dry run** walks the flow's stages in order, about 0.7 s each: their steps go queued → running → passed and approval gates show skipped, ending "Dry run passed. N steps in Xs. Gates were skipped."; it is refused while the graph has a cycle. Validate and Dry run run in the browser and send no request. **Save as change** commits only `.cinder/flows/<name>.yml` to the target branch, based on the commit the page loaded; if the branch moved since, the banner says so and the designer reloads. A banner shows a cycle while one exists, and any error the server would reject the flow for (such as `needs` naming a missing step); Save as change stays disabled until the flow is valid and reads "Saving…" while it runs. An edit clears the last Validate result. If the commit fails, the new change is closed rather than left empty.
- Triggers: `on: [push]` runs on each push to the default branch, `change` on each push to a change, `cron` when the flow's `cron:` (five fields, UTC) falls due, checked every 10 minutes.
- Steps: `run` commands run on the worker that claimed the run. A `deploy:` to a Cloudflare environment syncs it through `cinder-pipeline` and passes once the sync is Synced. `uses: cloudflare/workflow` with `workflow: <name>` starts that Workflow and shows `wf-id · step n of m`, then a line per Workflow step (`<name> · done` or `<name> · pending`). An `approval:` step raises a Flow approval item on Needs you; **Approve** lets its dependants run, **Reject** or **Dismiss** fails it. `approval:` (the designer's **Approvers**) names the role that may decide: only owners and people holding that role resolve the item.
- A Deploy step with an `aws:`, `gcp:`, `azure:` or `ssh:` map runs on the worker, which reads the map's credential from [Keystore](keystore.md) with the step's secrets and masks it in the step's log. A credential that isn't saved fails the step with `missing secret NAME: save it in Keystore`.
  - **AWS:** with `secret`, that secret is an AWS credentials file; with `role_arn`, the `aws` CLI assumes that role over OIDC with the web identity token saved as `AWS_WEB_IDENTITY_TOKEN`. `AWS_REGION` is the step's region. Then the step's `run` command runs.
  - **Google Cloud:** with `secret`, that secret is a service account key JSON; with `provider`, `gcloud` uses workload identity federation through that provider with the token saved as `GCP_WEB_IDENTITY_TOKEN`. The step's region is gcloud's default region. Then the step's `run` command runs.
  - **Azure:** with `secret`, that secret is `{clientId, clientSecret, tenantId}` JSON; without it, `AZURE_FEDERATED_CREDENTIAL` is `{clientId, tenantId, token}` JSON for a federated credential. The worker signs in with `az login`, selects the subscription, then runs the step's `run` command.
  - A cloud Deploy step without a `run` command fails with "deploy to <target>: set the step's run command, run after signing in".
  - **SSH:** the worker reads the host's keys with `ssh-keyscan`, keeps only the one whose `SHA256:` fingerprint is the saved one, and runs the step's Command with `ssh` over `key_secret`, accepting only that key. A host whose key does not match fails the step with "host key of <host> does not match the saved fingerprint …: refusing to connect".
- Any other deploy to AWS, Google Cloud, Azure or SSH runs its step's `run` command on the worker; without one the step fails.
- In the designer, a Deploy step whose Target is not Cloudflare shows that target's fields below Target and Environment, saved under the step's `aws:`, `gcp:`, `azure:` or `ssh:` key. Changing Target swaps these fields and keeps every other field of the step.
  - **AWS:** Authentication (Assume role (OIDC) with a **Role ARN**, or Access key from Keystore), Region, Service (Lambda, ECS, App Runner), Resource.
  - **Google Cloud:** Authentication (Workload identity with a **Workload identity provider**, or Service account key from Keystore), Region, Service (Cloud Run, Cloud Functions), Name.
  - **Azure:** Authentication (Federated credential, or Client secret from Keystore), Subscription, Resource group, Service (Container Apps, Functions), App.
  - **SSH:** Host, User, Command, Known host fingerprint (`SHA256:…`), Key secret.
  A credential is picked from the Keystore names of this repo and global ones, never typed; Validate rejects a value that isn't a secret's name, a region that isn't an id like `eu-west-1`, and a service outside the list.
- A step's credential (`secret`, or `key_secret` for SSH) names a [Keystore](keystore.md) secret, read for the job (flow, environment, repo or global scope, most specific first) and masked in logs. A worker without the target's CLI fails the step with "`<cli>` CLI not found on this worker's PATH". Each deploy is recorded in the environment's history on [Environments](environments.md).
- `setup: { <tool>: "<version>" }` on a `run` step puts that toolchain version first on the step's `PATH`. Tools: node, python, go, rust, dotnet, java, ruby, php, terraform, helm; a version starts with a digit and holds only letters, digits, `.` and `-`. A version the worker image already bakes is used as is. Any other version is unpacked from the tool cache in R2; the first run that needs it downloads the official release (node from nodejs.org, go from dl.google.com, terraform from releases.hashicorp.com, helm from get.helm.sh), checks the release's published SHA-256, and stores it there for later runs. A downloaded release that fails its checksum fails the step; a cached copy that fails it is replaced with a fresh download. A flow that fails validation is refused with a 400 naming the step.
- Jobs: `job: <name>` on steps of one stage groups them into one job, its steps in file order; a step without `job` is its own job named after the step. A job name is unique in its stage.
- `matrix: { node: [20, 22] }` plans one leg per combination of its lists (`node 20`, `node 22`); `shard: 3` plans legs `1/3`, `2/3` and `3/3`. Together they give at most 32 legs per job. A leg's steps get `CINDER_LEG` (its name, such as `node 20, 2/3`), `CINDER_MATRIX_<KEY>` per matrix value (the key upper-cased, `-` and `.` as `_`, such as `CINDER_MATRIX_NODE=20`) and, when sharded, `CINDER_SHARD_INDEX` (1-based) and `CINDER_SHARD_COUNT`.
- `runs-on: [label, …]` gives a job's runner labels: only a worker whose pool carries every one of them claims the job, and a job without `runs-on` takes the flow's top-level `runs-on`, else runs on any pool ([Workers](workers.md)). `junit:` and `artifacts:` take a list of relative paths.
- `stages: { <stage>: { needs: [<stage>, …] } }` orders stages; without it stages follow their first appearance in the file. Needs name stages of the flow's steps, and a cycle between stages is refused like one between steps.
- Runs of a flow that uses `job`, `matrix`, `shard`, `stages`, `retries` or `concurrency` are split into jobs: each job and leg of a stage is queued as its own `flow` job, so any number of workers can run a stage's jobs at once. A stage's jobs are queued once every job of the stages it needs has passed; a failed job skips every job of the stages after it and fails the run. A failed job is queued again, up to its steps' highest `retries` more times (each a new attempt), before it counts as failed. `concurrency: queue` starts a run only once the flow's older runs have finished; `concurrency: cancel` cancels the flow's unfinished runs on the same branch (or change) when a new one starts; `parallel` or none lets runs overlap. A flow with none of those keys runs as one `flow` job, as before; each of its steps' lines also reaches the step's log every 500 ms or 200 lines, every line before the step's status, and its `##[error]` and `##[warning]` lines are recorded as the run's annotations. Runs are numbered per flow (1, 2, …).
- In such a job the worker runs the steps in order; a step that fails skips the rest of the job and fails the job. Each step's log starts with its command as `[command]<cmd>` and reaches cinder every 500 ms or 200 lines, each line stamped with when it was printed. `##[group]`, `##[endgroup]`, `##[error]` and `##[warning]` lines a step prints stay in its log; `##[error]` and `##[warning]` lines, optionally written `##[error file=app.js,line=3]message`, are also recorded as the run's annotations. Cancelling a job stops its running step (SIGTERM, then SIGKILL 10 s later), marks it cancelled and skips the steps after it.
- The page reads its repo and default branch from `GET /api/repos/:repo`, so its flows load alongside the sidebar's repo and account lists instead of after them.
- `GET /api/repos/:repo/flows?ref=` lists the flows at the head of ref with each one's trigger, triggers, health (passed, failed, outcomes, trusted) and last run; `GET /api/repos/:repo/flows/:flow?ref=` answers the file's YAML, its parsed definition (null, with every error as `file:line: field: problem` joined by `; `, when the flow doesn't validate; such a flow is listed with no triggers), the head commit and each step's status and duration in the flow's last run.
- Cancel a run (`POST /api/repos/:repo/flow-runs/:id/cancel`, repo.write): every queued and running job is marked cancelled and the run fails; a worker running one stops at its next heartbeat.
- A job ends however it gets stuck: each step stops after 30 minutes, every call a worker makes to cinder gives up after 5 minutes, and a job still running after 1 hour 30 minutes fails with "timed out after 1h30m0s". A flow job running past 2 hours is failed by cinder itself and its worker stops at its next heartbeat.
- A change's new head cancels the runs its older heads still have queued or running for the same flow.
- Re-run a finished run (`POST /api/repos/:repo/flow-runs/:id/rerun`, repo.write) with `scope` `all`, `failed` (failed, skipped and cancelled jobs) or `job` with the job's `key`. It answers the run's new attempt number; each re-queued job's attempt goes up by one and its step logs, annotations and test results are cleared, while the other jobs keep theirs. A run that is still going is refused with 409.
- After a step with `junit:`, the worker parses each JUnit file and sends its passed, failed and skipped counts and failed test names; `GET /api/repos/:repo/flow-runs/:id/tests` lists them per suite (the file's path) and job. In a job of a run this happens in its **Upload artifacts** step. A file that can't be read or sent is noted in the log and doesn't change any step's status.
- After a step with `artifacts:`, the worker uploads each file (at most 100 MB) under its file name. `GET /api/repos/:repo/flow-runs/:id/artifacts` lists them with job, size, expiry (30 days after upload) and a download URL; `GET …/artifacts/:name` downloads one (repo.read).
- A flow file that doesn't validate never runs and is never saved. On each push and change, and on cron when its schedule is due, it gets a **failed** run with one job, **Validate flow**, whose log lists every error as `.cinder/flows/<name>.yml:<line>: <field>: <problem>` and which holds an error annotation per error on that file and line; it can't be re-run (409), a fixed file runs on its next push. On a change, every flow run of the head is one of the change's checks (`flow`, pass, fail or pending), so this run shows as a failed check. **Run flow** (`POST /api/repos/:repo/flows/:flow/runs`), **Save as change** (`POST /api/repos/:repo/commits`) and a file edit (`POST /api/repos/:repo/changes/edit`) of an invalid `.cinder/flows/*.yml` answer 400 `invalid_flow` with every error.
- Steps reach the network only through the worker's egress proxy, set as `HTTPS_PROXY` and `HTTP_PROXY`, which applies the pool's egress ([Workers](workers.md)); the hosts each job reached or was refused are reported like an agent's.
- `secrets: [NAME, …]` gives every step those Keystore secrets as environment variables, masked in step logs. A secret that is not saved in Keystore for the repo or flow fails every step before any starts, and each step's log names the secret.
- `secrets: [NAME, …]` on a step gives only that step those Keystore secrets, read just before it runs and masked in its log. A step secret that can't be read fails that step alone: its log reads `missing secret NAME: save it in Keystore`, run detail shows **Missing secret** NAME with a **Save it in Keystore** link to Keystore (a job of several steps lists the missing secrets of all of them, including a step skipped because one it needs failed), steps that need it are skipped and independent steps still run.

### Flow file schema

A flow file matches this schema exactly. Any other key is an error that names it, its line and the closest valid key (`steps.test.need: unknown key; did you mean needs?`). Types are never coerced: a scalar where a list belongs is an error. A duplicate key, a tab in indentation, or YAML that doesn't parse is an error too. Values are plain or quoted scalars.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `name` | name | yes | Equals the file name without `.yml`. |
| `on` | list of `push`, `change`, `cron`, `manual` | yes | What starts a run. |
| `cron` | five-field cron string | with `cron` only | UTC schedule. |
| `env` | map of `KEY: "value"` | no | Variables every step gets. |
| `secrets` | list of Keystore names | no | Secrets every step gets. |
| `concurrency` | `cancel`, `queue` or `parallel` | no | How runs of the flow overlap. |
| `runs-on` | list of labels | no | Default pool labels for jobs. |
| `stages` | map of stage → `{ needs: [stage, …] }` | no | Stage order; an entry takes only `needs`. |
| `steps` | map of step name → step map | yes, at least one | The steps. |

A step:

| Key | Type | Required | Meaning |
|---|---|---|---|
| `stage` | name | yes | The stage it runs in. |
| `needs` | list of step names | yes (`[]` for none) | Steps it runs after. |
| `run`, `deploy`, `uses`, `approval` | string | exactly one (`deploy` to a target other than Cloudflare also takes `run`) | A command, an environment to deploy, `cinder/verify` or `cloudflare/workflow`, or the role that approves. |
| `target` | string | no | Deploy target (Cloudflare by default). |
| `aws`, `gcp`, `azure`, `ssh` | map | no | Target sign-in, above. |
| `workflow` | name | with `uses: cloudflare/workflow` | The Workflow to start. |
| `if` | string | no | Condition. |
| `secrets` | list of Keystore names | no | Secrets this step alone gets. |
| `setup` | map of tool → version | no, `run` steps only | Toolchains, above. |
| `job` | name | no | Groups steps of a stage into one job. |
| `matrix` | map of key → list | no | Matrix legs. |
| `shard` | whole number ≥ 1 | no | Shard legs. |
| `retries` | whole number ≥ 0 | no | Extra attempts of a failed job. |
| `runs-on` | list of labels | no | Pool labels for its job. |
| `junit`, `artifacts` | list of relative paths | no | Test reports and files to upload. |

A name is 1–64 of letters, digits, `.`, `_` and `-`, starting with a letter or digit.

```yaml
name: ci
on: [change, manual]
stages:
  test: { needs: [build] }
steps:
  install: { stage: build, run: "npm ci", needs: [] }
  unit: { stage: test, run: "npm test", junit: [reports/junit.xml], needs: [install] }
  verify: { stage: test, uses: "cinder/verify", needs: [unit] }
```

## Backed by

A D1 `flow_runs` row per run with a `flow_jobs` row per job (`flow_step_runs` holds step timings, `flow_run_attempts` re-runs, `flow_tests` test suites), step logs and artifacts in the R2 bucket `cinder-logs` (live log lines reach the page over the repo's live socket), and a D1 job per queued flow job, run by any worker that takes `flow` jobs (the managed pool or a BYO pool); Cloudflare steps go through Workflows, approvals through Needs you, secrets through Secrets Store, `setup:` toolchains through the R2 bucket `cinder-ci-cache`. The page's **Backed by** link opens the `cinder-pipeline` Workflow.
