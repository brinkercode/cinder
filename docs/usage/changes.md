# Changes

## Purpose

Every intent and every change on the repo, from a written intent to merge, on one board. The verifier owns the merge.

## Where

Code ▸ *repo* ▸ Changes (`/:repo/changes`, a change at `/:repo/changes/:id`, collisions at `/:repo/changes/collisions`)

## What you can do

- Every change is numbered within its repository when it is created (1, 2, 3 …) and has a key: the repository name in capitals without punctuation, a dash and the number (`pulse` gives `PULSE-12`, `web-store` gives `WEBSTORE-3`). A change is named by its key wherever it has one: change cards and rows, the change page's header and its branch ("wants to merge PULSE-12 → main"), the branch menu's change workspaces and Code's workspace views. A change's URL is `/<repo>/changes/<KEY>` (`/pulse/changes/PULSE-12`), and every link to a change uses its key; a URL with the change's id still opens it. The id stays behind the header's copy button and on hover. A change's merge commit subject is `<KEY>: <title>`, with the id in its `Cinder-Change` trailer. A new change's fork is named `<repo>--<KEY>`; changes made before numbering keep their old fork names and were numbered by creation time.
- On a repository with no code: an empty state with **Describe a change** (opens New change) and **Quick setup** (opens Code).
- While the token budget pauses agents, a banner reads "Agents paused: budget reached · spent of budget tokens · resumes <date> or when an owner raises it". **Raise budget** opens [Needs you](needs-you.md); a person who isn't an owner sees it disabled, with "Only owners can raise the budget: <owners>" and **Ask <owner>** (an email to the first owner).
- The board has six lanes: **Intents** (open issues nobody has a change for), **In progress** (draft and planned changes, and intents claimed by an agent until its first commit lands), **Verifying** (checks running, repairing, failed or conflicting), **Needs review** (awaiting a person's approval or with changes requested), **Merge queue** and **Merged · 24h**. Each issue and each change appears once: a change linked to an issue carries its `#n`, and that issue has no card of its own. A repo with nothing open shows "Nothing in flight" with **New intent** and **Describe a change**.
- Intent cards have a dashed border, `#n`, priority, labels, "by <author> · <age>", a **Move to…** menu and **Hand to agent**. A claimed intent keeps its intent card in In progress with a chip naming its agent, or "racing 2"; when the agent's first commit lands it turns into a change card in Verifying without a reload. Change cards show one meta row (the change key such as `PULSE-12`, or the change id's first 8 characters for a change without one, `#n` when linked, author and age) with a p(merge) pill, the title (two lines at most; hover for the full title), its labels and priority pill, the agent's live activity when it reports one, a red why-line when it is blocked, then +adds −dels, files and tokens. Long titles, ids and why-lines wrap or clip inside the card, and badges wrap onto a new line, at any lane width.
- p(merge) is the agent version's merged changes over its decided (merged, failed, closed) changes on this repo. Under 20 outcomes it reads "untrusted: n outcomes" (or "no outcomes yet"), never a percentage. A change someone drives has none. Toolbar: **Board** / **Table**, "Into <target>", **Collisions**, **From a branch** and **Describe a change**. Tiles: Intents waiting, In flight (in progress, verifying, merge queue), Needs review, Merged · 24h and Verifier pass rate, which shows "untrusted: n outcomes" until the verifier has the repo's trust threshold of outcomes.
- Search matches title, `#n`, change id, author and labels, over the loaded items without a new request. The segments **All**, **Agents**, **People** and **Needs you** (its count is the Needs review lane: awaiting approval plus changes requested) filter the same items. **Label ▾** (a filter field over the board's labels, or "No labels yet" with **Open Settings** when there are none), **Priority ▾** (P0–P3) and **Sort ▾** (Lane order, Priority with P0 first, or Oldest first) combine with them and stay set across reloads and live updates. **Refresh** reloads.
- Clicking an intent card opens its drawer: label chips (× removes; **+ Add** picks a label or creates the one you type) and **Priority**. Each edit saves at once and the card shows it.
- **+** on Intents opens a title field: Enter adds the intent at once and files it as an issue; if that fails the card goes and the error shows. Esc closes the field. **Table** lists Item, Title, Stage, Who, p(merge), Diff, Tokens and Age, plus closed changes with the stage Closed.
- Drag an intent card (or pick a lane in its **Move to…** menu with the keyboard) between **Intents** and **In progress**, including an intent an agent claimed that has no commit yet. Into In progress claims it for the top suggested agent (`POST /api/repos/:name/issues/:n/claim`); back to Intents releases it (`DELETE …/claim`), which closes its agent's change. **Hand to agent** does the same as dragging to In progress. The card moves at once, and a reload that started before the request answered doesn't move it back; if the request fails it moves back with the error under the toolbar, and once an agent has committed it reads "An agent already committed; the verifier owns it now." Dropping any card into Verifying, Needs review, Merge queue or Merged shows "Past In progress, only the verifier moves work." and sends nothing. Change cards (a commit landed) don't drag.
- Click an intent card in Intents to open its drawer on the right: the body, labels and target branch, then **Who writes it**: the best agent version on this repo with its p(merge) ("untrusted: n outcomes" below the trust threshold), **Race two agents** (the top two, with the challenger's untrusted count) and **I'll write it**. **Start** claims it for the pick; I'll write it opens New change on **I wrote it** with the title starting `#n`, so the change links the intent. **Close intent** closes the issue.
- Without `repo.write` on the repo, drag, **Move to…**, **Hand to agent**, **Close intent** and **Start** are disabled; their tooltip and a line above the board read "Moving intents needs repo.write on this repo." The board's `can_write` says which.
- The board updates live: a moved item changes lane in place, a closed issue leaves the board and an agent's activity updates its card's live line. With live updates off it reloads every 15 seconds.
- A failed change stays open in **Verifying** until it is retried or closed, with the step it failed at as its red reason ("Failed at verify: 3 tests failed", or "Failed" when the step gave no reason); a conflicting one reads "Conflicts with its target". Any open change the guard blocks shows a red why-line instead, the same text as its Needs you item: "Blocked: quarantined (…)" or "Blocked: new dependency p-retry 6.2.1 needs approval". It goes once the item is resolved. It counts as open on the change header's "n of m open", the branch list and the repo's card under All repositories. Its card offers **Retry verify** and **Close…** (the same confirm as on the change); a retry that doesn't start shows "Retry didn't start: …" on the card.
- Cards and table rows show the diff as +adds −dels and files changed for any change with a head (its head's compare when there is one, else the counts its **Files changed** tab shows, counted once per head commit and kept), and the change's token total (— when none). The board reads these with the work list; it sends no request per card. A change someone drives shows the person icon and "written by hand". Change ids show their first 8 characters; hover for the full id, and copying the id copies the full id.
- A change's timeline names who did each step and links to it: the agent version (its Versions tab), the judge that decided a lease or a route (its calibration), the runner that ran a job and its pool (Workers), a git push, or the person.
- Intents and changes share one priority scale, P0 to P3 (a change without one counts as P2). A change's priority orders agent work: runners claim a P0 change's queued jobs first, then P1, P2 and P3, and within one priority by risk, then oldest first. `PATCH /api/changes/:id {priority?, labels?}` (the author, the driver or `repo.write`) changes them, with the same checks as New change; the timeline records an `edited` event and the board updates live. `GET /api/repos/:name/changes` takes `label=`, `priority=` and `sort=priority|age` (age, the default, is oldest first; sort applies to open changes), and `GET /api/repos/:name/work` takes `label=`, `priority=P0..P3` and `sort=priority|age` (age keeps board order). A change's board card shows its own labels with those of its linked issue, and the issue's priority, else its own. Adding a label routes the change or intent by the repo's Label routing rules (Repo settings).
- Open `/:repo/changes?state=<state>` (Insights' **View failing changes** uses `state=failed`) to see only changes in that state.
- **New change** (`/:repo/changes/new`) has two modes, picked with two cards at the top; switching keeps what you typed in each. Both show the target branch, which follows the top bar's branch switcher. **Describe a change** on Changes and **New change** on Code open **Describe it**; **From a branch**, or a URL with `?head=`, opens **I wrote it**. The empty Changes page offers both. New change is for an intent with no edit; an edit goes to an agent from Code's editor (**Hand to an agent**). Judges, an environment's **Reconcile** and a closed change's **New change from intent** open it with the intent filled in; the URL has no intent parameter.
  - **Describe it**: write the intent in prose (`@agent@version` and `#change` suggest as you type; one change per bullet line if ticked), pick the agent version (stable by default, with its win rate or "not enough races"; the change records the version it resolved to as agent@vN), and optionally acceptance criteria, labels and priority. **Save draft** and **Hand to agent** enable at 8 characters and are disabled while the request is pending, so one click makes one change. The Prediction rail updates as you type; when the target's newest commit isn't indexed yet (a merge just landed), it predicts from the newest indexed commit and queues the index. Each person gets 30 previews a minute (`POST /api/repos/:name/changes/preview` answers 429 `rate_limited` past that). Each person may create or propose from Code 30 changes a minute per repo, past which the request answers 429 `rate_limited`; another person on the same repo is unaffected. The change has no head branch; the agent develops it and its card names it. You return to the board with a confirmation. When the target's head has no symbol index yet, the change waits in Planned while a runner indexes it, then leases the symbols predicted from that index.
  - **I wrote it**: pick the head branch you pushed (or push to `refs/for/<target>`; if the branch list fails to load, only the head in the URL is offered and the rest of the page loads as usual) to see its commits, files and +/−, then a title (prefilled from the branch name), a description and at least one reviewer. **Let agents push to it** is off by default. Off, an agent's commit to the change is refused (403 `agent_push_refused`), and an `@agent` message on it is answered in a review thread instead of commits, with an `agent_push_refused` event naming the agent on the timeline. On, agents may commit to it. The driver or an owner changes it later with `PATCH /api/changes/:id {agent_pushes}`. **Open as draft** and **Open change** stay disabled until there's a head branch, a title and a reviewer; their tooltip says what's missing. The change carries the branch's commits, you drive it, and no agent develops it: it goes straight to verifying, with a verify job on the branch's head commit (a draft does when marked ready); the change's fork moves its target branch to that commit first, so a later rebase and merge carry the branch's commits. You land on the new change's page with a confirmation.
- With the repo's Git credentials (`POST /api/repos/:name/git-credentials`), `git push origin HEAD:refs/for/<target>` opens a change on `<target>` with the pushed commit that you drive: no agent develops it, and it goes straight to verifying on that commit. The change's title is the subject line of the pushed commit's message and its intent the whole message; a commit with no message is titled `Pushed <sha> to refs/for/<target>`. It appears on the board without a reload.
- Every new commit on a change you drive re-runs verify on it: a push to its head branch (cinder copies the commit into the change), or a commit to it from Code or a workspace, whatever the number of files. The change's head moves to the commit and a `pushed` event naming it joins the timeline. A change in `planned`, `leased`, `verifying`, `needs_fix` or `failed` goes (back) to `verifying`; one in `in_queue` or `converging` goes to `needs_fix` first, so its old head never merges; a newer commit cancels the verify still queued or running on the older one, so one verify runs per change.
- A verify's log starts with **Fetch change** (the head it merged onto the target branch and the target's short sha, with the diff stat) and **Check leases** (each file the change touches with the leases granted on it, or `none`); a failed verify's reason is the check's output after them. A verify that can't merge the change onto a target that moved under it doesn't fail the change: it converges onto the new target, and a real conflict goes to the resolver. If the conflict is still there right after a clean converge (it's with a change merged ahead of it in the queue), the change goes to **conflict** instead of converging again.
- Every push to a change (an agent's develop or resolve, or an edit from Code) and its final diff at verify are checked against its lease, symbol by symbol. A written symbol no other change leases joins the change's lease. A written symbol another change leases puts the change in `conflict`: the push stays on the change, the conflict records each such symbol with its holder and whether the write changed its signature or its body, and the change can't enter the merge queue until the conflict is resolved.
- On a change: copy its full id from the header; tabs **Conversation**, **Files changed**, **Checks** and **Commits**; comment on a line, **Review** (approve or request changes, on any open change whatever its review route; the popover closes and clears once the review is posted; an approval turns Human approval green but only queues a change routed to a person or whose requested reviewers have now all approved; for someone without `change.approve`, **Approve** and **Request changes** are disabled and the popover reads "Only approvers can approve or request changes: <names>. You can still comment.", from the change's `can_approve` and `approvers`; a comment needs only `repo.write`), **Take over** or **Hand to an agent**, **Edit in Code**, **Add to merge queue**, **Close change**. While an action is sent and the change reloads, the page body is marked busy and a second action is not sent; **Close change** is disabled. **Auto-queue** saves in place: only the toggle changes, the page neither reloads nor moves, and a refused save turns the toggle back with the reason under it. Turning it on for a verified change nothing else holds queues it at once.
- In the rail, label chips (× removes; **+ Add** creates the label you type and press Enter on) and **Priority** (P0–P3, with "Higher priority queues first and is picked up first by agents.") save at once and show on the change's board card. Merged, closed and failed changes show their labels read-only.
- On a change a person drives, the rail's **Agent pushes** (after Lease) has **Agents may push**: it shows the change's `agent_pushes` and saves on click (`PATCH /api/changes/:id {agent_pushes}`; the driver or an owner). Off, an agent's commit is refused and the timeline shows "push refused: Agents may push is off · n commits not applied" with the agent@version and **Allow agent pushes**, which turns the toggle on so the agent's next push lands. Turning it on after a refused commit queues the refused develop job again, once.
- One merge gate decides every merge: a change at the head of its merge queue gets a merge job only with a passing verify verdict on its current head, a clean guard result for that head (a quarantine, an unapproved dependency or a guard result for an earlier push blocks), a person's approval of the head when its route is human, an approval from each requested person, no open findings and, when the repo requires it, no unresolved threads. Until then the queue shows why it is stuck. A queue head with no pushed head goes back to `needs_fix` and leaves the queue, and the changes behind it re-verify without it. The change's `blockers` list is the same gate: it is empty exactly when the change can merge.
- Review route: after verify, the risk judge routes the change. A trusted low answer within the branch rule merges on green; otherwise the reviewer agent reviews it, and its pass queues the change with no approval needed. That includes every change while the judge is still untrusted, so a new repo merges without a person, and each agent review is recorded as a risk judgment scored like the judge's. A person approves only a trusted high answer, a path the branch rule routes to people, a destructive deploy plan, or any change when no reviewer agent is released. A change whose diff only edits documentation (`*.md`, `*.mdx`, `*.txt`), or only comments and blank lines in code files (a line comment, or a block comment opened and closed on that line with nothing after it), routes as a trusted low answer whatever the judge says, with the reason "documentation-only change" or "comment-only change"; a path the branch rule routes to people or a destructive deploy plan still goes to a person. Any changed code line, or a file too large to diff, keeps the judge's route.
- Requested reviewers hold a change: while any requested person has not approved its head, a verified change stays in `verifying` even with Auto-queue on, and **Add to merge queue** is refused. The last one's approval queues it when Auto-queue is on. `DELETE /api/changes/:id/reviewers/:who` (the author, the driver or `repo.write`) removes a requested reviewer, and removing the last pending one queues it the same way; the timeline records who removed whom and who auto-queue still waits on. A clean agent review doesn't release a change a requested person still holds. The change's `review.requested` lists each requested reviewer with `pending` or `approved`; only an approval of the current head counts. Merge readiness gets a requested-reviewers row while any person is requested: "Waiting on jon, sam (requested)" (with who already approved the head), or green "Requested reviewers approved"; the line under **Auto-queue** says the same.
- In the rail, **Request** next to Reviewers opens a picker (not on merged, closed or failed changes): a search field, **Suggested** (owners of the touched paths with how many of them they own, never someone already requested), **People** (only for people managers; empty for anyone else) and **Judges** (scores, doesn't approve). Picking one requests them: they appear under Reviewers as `requested` and Pending, and Human approval names them at once. A search with no match says so and points to Access & people; a failed load or request shows inline in the picker. Each requested reviewer has **×** to remove them. The picker works by keyboard: the search field takes focus, Tab reaches every row, Esc closes it and returns focus to **Request**.
- On a change's Conversation tab every review thread is a card with its path and line (or "On the change"), its comments, a **Reply** field (Enter sends) and **Resolve**. A thread with a suggestion shows the old and new line and **Apply suggestion** (you must be driving the change): it commits the suggestion to the change, the block then reads "Applied in <sha>" and the verifier re-runs. A resolved thread collapses to "Resolved by <who> · n comments" with **Reopen**. Merge readiness lists `n unresolved threads` (the `threads_unresolved` blocker when the repo requires resolved threads) or "All threads resolved".
- On a change, **Files changed** shows the files its commits change, with +/− per file, against the newest commit it shares with its target, **Commits** its commits not on the target and **Checks** the checks on its head; each shows an empty state when there are none. A quarantined test failing at the head is a `quarantined` row with its flake rate, since when, "excluded from the verdict" and **Manage** (Repo settings ▸ Flaky checks); it doesn't count as a failed check. **Merge readiness** follows the change's state, checks and latest review, and shows the queue position while the change is in the merge queue. Ready and **Add to merge queue** follow the same rule the queue applies, reported as the change's `queue_blocker` (null when it can queue): verified at its current head ("No head pushed" while it has none), then approved as its route and requested reviewers need. While something blocks it the button is disabled and the line under it names the blocker ("Blocked: Verifier hasn't passed the head."); a refused queue (409 `not_ready`) shows its reason on the page. On a failed change its first row names the step it failed at and the reason the runner reported ("Failed at develop: …"). A change the guard blocks gets a red row with the same "Blocked: …" text as its card and Needs you item, with **Decide in Needs you**; it goes once the item is resolved. After a person's **Request changes** the pill reads Changes requested. A failed change's pill reads Failed and a red strip reads "Failed at <stage>." with the reason, plus **Retry verify** and **Close change…**; the rest of the change is read-only. **Retry verify** (or `POST /api/changes/:id/retry`, or `cinder change retry <id>`; needs write access) sends it back to `verifying` with a fresh verify job and its repair count reset; any other state answers 409 `not_failed`. The job re-runs only the tests failing at the head (the detail's `failure.check` names them, when any were reported): the repo's check gets them in `CINDER_ONLY_TESTS`, one per line. While it runs the pill reads Verifying, the strip reads "Re-running the failed check <tests>; the n passing checks are kept" and the Verifier row reads "checks n/m". A retry that doesn't start shows "Retry didn't start: … The change stays failed." **Close change…** asks first: it warns that the leases release, the agent stops and closing can't be undone, and takes an optional reason (`POST /api/changes/:id/close {reason}`, at most 500 characters). A closed change is final: its pill reads Closed, the strip reads "Closed by <who> <when> ago · <reason>. Closed changes can't reopen." with **New change from intent** (New change prefilled with the same intent), there is no Review, Take over, merge queue, Auto-queue or comment box, and the timeline's closed event shows the reason. The change carries `closed_by`, `closed_at` and `close_reason`. A draft change shows a strip "Draft. The verifier doesn't run on a draft." with **Mark ready** (`POST /api/changes/:id/ready`; its author or an owner): the change moves to `planned`, and a change a person drives goes straight on to `verifying`. The pill reads Verifying, the strip reads "Verifier starting on <sha> · usually under 10s" and the Verifier row "Verifier queued" until the first check lands. A refused call shows "Couldn't start the verifier: … The change stays a draft." with **Try again**.
- A change an agent drives repairs itself: when its verify fails or a review requests changes, it goes back to `needs_fix` and cinder queues a develop job for the next repair round, carrying the failing log tail or the review's unresolved threads. Each round adds a `repair_started` event (round, max, failed check), and the change carries `repair: {round, max, check}`. `GET /api/changes/:id/repairs` lists every round in order: the check it fixes, what the agent's develop run reported, the verifier's verdict and reason, and the tokens used. The limit is the agent version's `limits.max_repairs` (2 when unset). A failure past the limit fails the change with the reason "repairs exhausted (m of m): <last failure>"; its card and strip read "Failed at repair limit". A change a person drives (Take over, or opened from a branch) stays in `needs_fix` until its driver acts. A guard quarantine that lands after verify passed sends an agent's change back to `needs_fix` too, with the finding as the failure (its queued verify is dropped); a person's quarantined change waits for them with the **Change quarantined** item. A failed develop or resolve job on an agent's change runs once more on the agent's other version (its canary or stable, else dev-open for the developer), recorded as a `retry` event; if that fails too the change fails. A max-spend or max-tokens stop never retries.
- While a change repairs, its card stays in **Verifying** with "Repairing · round n of max · fixing <check>" under the title. Once a fix passes verify the change no longer reads Repairing, even while it waits for review or the queue. On the change, the status pill reads **Repairing**; a strip under the header shows one pip per round (done, current, left), the agent, the check it is fixing and the failing test, with **Open run** (opens Checks); the Verifier row reads "Verifier repairing · round n of max". The timeline has one event per round, in order: what the agent changed, the verifier's result and the tokens used; the current round shows a spinner. While the rounds load they are bones in a **Repair rounds** card, and a failed load shows an inline error with **Retry**; the change's other events show either way.
- When the last round fails too, the pill reads **Failed** and the strip turns red: "All max rounds used and <check> still fails. It needs a person.", with **Retry verify**, **Take over** and **Close…** (asks to confirm first). The card in **Verifying** shows the same line with **Retry verify** and **Close…**; a refused action shows its reason on the card.
- Leases: a change holds the symbols it leased while it is developing, converging, verifying, resolving or in the merge queue, or while a job runs for it. Parked in `needs_fix` or `conflict`, or taken over with no job running, it keeps them only for an idle window (30 minutes from its last event; `lease: { idle_minutes: <n> }` in `.cinder.yml` changes it). Past it the lease is released, a `lease_expired` event joins the timeline, and the change's next develop or verify job waits until it re-acquires the lease; a failed change re-acquires it the same way when retried. Changes waiting on a symbol get it in arrival order, a higher-priority change first; a change waiting on a running change also keeps later changes off the rest of its lease. A change that leaves the merge queue to resolve a conflict, or a queue head whose merge is refused (the target moved, its speculation or verdict is stale, or the merge failed) and rebases, re-enters it at its old position. A change that enters the queue after a change stacked on it goes to the front, so it merges first. A re-verify that passes while the change waits on a review or has Auto-queue off leaves it in `verifying`, where **Add to merge queue** can queue it.
- Collisions: when a push writes a symbol another change leases and the two edits really conflict, cinder records a collision for each such symbol. They conflict when the lines one replaced overlap or touch the lines the other replaced in that file, as in git's three-way merge; edits to different lines of one symbol (say a variable's description and its validation) both go ahead without a collision and merge in queue order. A holder that hasn't verified yet has no lines, so a write of its symbol collides. Each collision records the other change, signature or body, severity high for a signature and low for a body, p 1 for a held lease), sends the diagnostic to the colliding change's agent and a notice to the holder's. An agent's change is settled by cinder: a seam is proposed when the seam judge is trusted and finds a shared interface, otherwise the change is stacked behind the holder (also the default while the seam judge is untrusted), and the feed's action says which and why ("Stacked: the default while the seam judge isn't trusted"). A stacked change waits for the holder's push, develops on its head and merges only after it; if the holder closes, the stacked change is leased again and starts over on the target (the merge blocker "stacked on <change>, which merges first"). A person's change waits in conflict for its person, with no resolve job queued on it (as does any conflict on a change whose driver turned agent pushes off); cinder still asks the seam judge (the answer is scored like any other) and notes advice on each collision without acting on it. The card then reads "Collides with <change> on <symbol>", and the board's **Collisions · n** button opens [Collisions](collisions.md) (`/:repo/changes/collisions`). On the change, Conversation shows a collision card, the rail's **Symbols** lists Leased (with mode), Touched and Collisions with their state, and the readiness conflict row names the open collision. **Resolve** on the card (on both changes of an open collision, once per change) or on the Collisions page resolves every open collision of a person's change that ran into it: **Stack** waits behind the holder, **Seam** records a seam proposal for the symbols, **Hand over** takes the symbols from the holder's lease, **Go first** puts the change first in line; picking one shows what happens and the merge order after, and the button applies it. Each one schedules the change again, messages both agents and updates every open page without a reload (`POST /api/changes/:id/collisions/resolve {action}`). On a file in Code, **Live on this file** warns "<change> is changing the signature of <symbol>, which <change> leases" while another change has written a symbol the file's lease holder leases in the last 10 minutes.
- A change proposed from Code shows **Committing your edit…** in its header and Files changed until a worker commits the edit ("waiting for a worker" while none has claimed it). If the commit fails, it shows **Edit commit failed** with **Retry in Code**, which reopens the file in the change's workspace.
- While the board or a change loads, nothing shows for the first 150ms, then its skeleton; after 10s the skeleton adds "Still loading…" with **Retry**, which reloads.
- A change draws its header, timeline and rail before its diff arrives: until then the Files changed tab has no count, the diff totals are hidden and the tab shows a loading placeholder (or the files' load error with **Retry**). Hovering or focusing a card on the board starts loading that change, so opening it shows data already on its way.

### Issues

Issues live on this board. An old `/:repo/issues` link opens Changes, keeping the query string, and `/:repo/issues/<number>` opens one issue from its card.

- Open an old Issues link; it lands on the repo's Changes page.
- Open `/:repo/issues/<number>` to see one issue: its title, Open or Closed state, description, assignee, labels and linked changes (each links to the change and shows its state).
- Read the issue's comments, oldest first, and post a comment with **Comment**.
- Close the issue with **Close issue**, or reopen a closed one with **Reopen issue**.
- Set an issue's priority (`P0` to `P3`, or null) and labels with `PATCH /api/repos/:name/issues/:n {priority?, labels?}`; labels are non-empty strings. Agent work is ordered by the priority of the change, set with `PATCH /api/changes/:id` (see [Changes](changes.md)).

The issue page reads `GET /api/repos/:name/issues/:n` and writes `POST …/issues/:n/comments` and `PATCH …/issues/:n {state}` (D1). Controls to edit an issue's priority, labels and assignee are planned; until they land, use the API above.

## Your first change

A change needs a repo with a branch to build on and a check that passes. [demo/pulse](../../demo/pulse) is one: its check (`npm test`) needs only Node. Publish it as `main` of an empty public GitHub repo you create (for a private one, import it from Repositories ▸ **New repository** with a read token), then, with `live.env` loaded and both runners up ([Register a runner](../operations/README.md#register-a-runner)), from the repo root:

```sh
git push https://github.com/<you>/pulse.git "$(git subtree split --prefix demo/pulse)":refs/heads/main
cd runner
go run ./cmd/cinder repo add pulse --import https://github.com/<you>/pulse.git
go run ./cmd/cinder change new pulse "Add a /ping endpoint that answers pong"
go run ./cmd/cinder change show <id>   # the id change new printed
```

Or open the Worker URL, pick **pulse** and choose **New change**. The change moves through `developing`, `verifying` and `in_queue` to `merged`; follow it on the change page or with `change show`. With a released reviewer agent it merges without you; a change routed to a person waits for you to approve it on its page.
